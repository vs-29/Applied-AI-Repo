Tiny GPT, explained from zero

You now have a small program that reads 1.1 million characters of Shakespeare and learns to write text that looks a bit like it. It works the same way ChatGPT does, at a far smaller scale. This page walks through what was built, in the order it was built, with the real numbers from your laptop's GPU.

The one idea

A language model only does one thing

It looks at some text and predicts what character comes next. That's all. To write a paragraph, it predicts one character, sticks it on the end, and predicts again. ChatGPT does the same thing with word-pieces instead of single characters, and with billions more numbers inside.

Everything else in this project is about making that guess better.

Step 1 · Tokenizer

Turning text into numbers

Computers can't do maths on letters, so we give every distinct character in the Shakespeare file a number. There are exactly 65 of them: newline, space, punctuation, 3, A–Z and a–z. This list is called the vocabulary. Try typing below.

Each box shows a character and its ID. In code these are encode() and decode() in bigram.py.

Step 2 · Training examples

The text quizzes itself

We don't need anyone to label data. Take any 8 characters as the input; the answers are the same text shifted one place to the right. One chunk of 8 is really 8 quizzes at once: after F comes i, after Fi comes r, and so on. get_batch() grabs 32 random chunks like this each step.

The first 9 characters of the file · hover a box

Hover an input box to see which quiz it is.

We keep the last 10% of the text hidden from training. That's the validation set. If the model does well on text it has never seen, it has learned patterns rather than memorising.

Step 3 · The training loop

Guess, score, adjust, repeat

A model is just a big pile of numbers called weights. At the start they're random, so the guesses are random. Training repeats four steps thousands of times:

GuessRun the model on a batch.model(xb, yb)
ScoreHow wrong was it? That's the loss.cross_entropy
BlameWork out which weights caused the error.loss.backward()
AdjustNudge each weight a little to do better.optimizer.step()

What the loss number means

Lower is better. A handy way to read it: e−loss is roughly how much confidence the model puts on the correct next character, on average.

Random guessing
4.17
1 in 65 → about 1.5% on the right answer. This is the starting point.

2.28
About 10%. Small numbers, but every 0.1 lower is a real improvement.
Milestone 1 · bigram.py

Model 1: look at one character only

The simplest model is a 65 × 65 table. Row t says how likely each character is to follow t. It has no memory beyond the single previous character, which is why it's called a bigram (two characters) model. Training fills in the table. Below are the real counts from the Shakespeare text, which is what the trained table ends up close to.

The problem: after e the table always predicts the same spread, whether the word was the or love. It can't tell. That's why its writing looks like this:

Milestone 2 · attention_demo.py → gpt.py

Model 2: let characters look back

Self-attention lets every character look at all the characters before it (up to 8 back) and decide how much each one matters. It can't look forward, because that would be peeking at the answer. The grid shows those decisions for the input First Ci. Each row is one character asking “who should I listen to?”, and each row adds up to 1.

Where the weights come from: query, key, value

Each character produces three small lists of numbers. Think of a library search:

Query“What am I looking for?” e.g. a vowel wanting the consonant before it.
Key“What do I contain?” Each earlier character advertises itself.
Value“What I'll pass on if you pick me.” The actual information shared.

Query × key gives a score for every earlier character. Softmax turns the scores into the percentages in the grid, and those percentages mix the values. Nobody writes these rules by hand. Query, key and value are all weights, so training learns what to look for.

Multi-head just means running several small attention layers side by side, each free to track a different pattern, then joining their outputs. With the same total size, 4 heads beat 1 head.

We also add a position embedding. Attention on its own doesn't know order, so “dog bites man” and “man bites dog” would look the same. Adding a learned vector for “1st position”, “2nd position” and so on fixes that.

How it was built

What happened on your laptop

  1. Made an isolated Python environment (.venv) so this project's packages don't clash with anything else. 
    python -m venv .venv
  2. Installed PyTorch with CUDA, the library that does the maths, built to run on your NVIDIA GPU. Then numpy and matplotlib. 
    .venv\Scripts\pip install -r requirements.txt
  3. Downloaded the training text, Tiny Shakespeare (1,115,394 characters), into data/input.txt.
  4. Wrote and ran the bigram model. 
    .venv\Scripts\python bigram.py
  5. Wrote the attention demo, which builds attention up in 4 small versions so you can see each idea on its own. 
    .venv\Scripts\python attention_demo.py
  6. Wrote and ran the attention model, twice, to compare 1 head with 4. 
    .venv\Scripts\python gpt.py --heads 1
.venv\Scripts\python gpt.py --heads 4

About charts: nothing has drawn a matplotlib plot yet. The scripts only print loss numbers to the terminal; the chart above was drawn from those printed numbers. Saving a real loss-curve image is part of Milestone 5.

Words you'll keep seeing

Glossary

Token
One unit of text the model reads. Here, a single character.
Embedding
A list of numbers that represents a token. The model learns these, so similar characters end up with similar lists.
Logits
The model's raw scores for each of the 65 possible next characters. Softmax turns them into probabilities.
Batch
A group of examples processed together (32 chunks here). GPUs are fast because they do many at once.
Step / iteration
One round of guess → score → blame → adjust.
Learning rate
How big each nudge is. Too big and training is unstable; too small and it's slow.
Tensor
PyTorch's word for a grid of numbers. Shapes like (B, T, C) mean batch × time (position) × channels (numbers per token).
